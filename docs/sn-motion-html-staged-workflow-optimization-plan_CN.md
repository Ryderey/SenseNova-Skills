## 1. 用户问题与目标

用户输入：“使用 sensenova 技能，将经典童话故事《小红帽》以故事页形式展示出来。”当前实际体验是 Agent 直接交付最终结果，用户看不到分镜、文案和图片的形成过程；发现情节不对或需要换图后，修改成本很高。

本次优化需要让用户在适当时机看到可审阅成果，并能通过自然语言精确修改已有成果。核心流程为：

**故事草稿 → 确认文案与方向 → 代表样图 → 确认视觉 → 完整图片总览 → 网页组装与交付 → 按幕局部修改。**

首版默认设置两个等待反馈的创作确认点。完整图片总览需要展示，但默认不增加第三次强制确认。用户明确要求直接完成时跳过创作确认等待，仍保留阶段展示和必要检查。已经给出的决定不重新询问。

成功标准不是“多发几条进度消息”，而是：用户能看到实际文案和实际图片；在后续制作前修改关键决定；离开后仍可继续；修改一幕不会无故重做整套故事。

## 3. 首版范围与非目标

### 3.1 首版必须完成

1. 改写技能入口与工作流，定义阶段产物、继续条件、等待行为和跳过规则。
2. 建立故事草稿和代表样图两个明确的创作确认点。
3. 展示带幕号的全部图片总览，并保留自然语言按幕修改入口。
4. 复用 `content/story.json`，记录阶段、决定、稳定章节 ID 与最少必要的生成依据。
5. 定义纯文案、单图、全局画风、章节结构、排版五类变更的影响范围。
6. 支持已有图片、旧项目续作、执行中断恢复和直接完成模式。
7. 同步中英文使用指南和技能入口文案，完成行为验收及必要回归。

### 3.2 首版实现边界

首版以技能文档和工作约定为主，复用当前运行脚本。故事草稿在对话中展示；样图直接展示；完整图片使用现有总览工具。无需新增审核平台、状态机框架或草稿导出器。

生产记录由 Agent 维护在现有 `docs/production-spec.md` 中，不新增必须由所有脚本读取的状态 JSON。工作流状态不进入前端运行时，最终网页不依赖工作记录。

### 3.3 不纳入首版

- 审核后台、拖拽分镜编辑器、批注系统、用户账号或协作服务。
- 数据库、任务调度器、通用依赖图、自动内容哈希失效系统。
- 新图片模型、新视频生成链路、默认生成视频或展示海报。
- 修改现有风格枚举、重构前端架构、全仓库格式化或修复无关历史问题。
- 自动安装到用户技能目录、部署站点、提交或推送代码；这些不因“执行本方案”而自动获得授权。

## 4. 交互模式与授权解释

### 4.1 默认协作模式

适用于“把一个故事做成网页”这类需要 Agent 决定情节拆分、实际文案和画风的新任务。

- 确认点 A：完整文案草稿与视觉提案已经可读，尚未调用新图片生成。
- 确认点 B：代表样图已经实际展示，尚未补齐剩余图片。
- 每个确认点明确提出一个当前阶段的问题，提供简单答法，例如“按这个方案继续”或“把第 3 幕改为……”。
- 等待确认时可以进行离线校验、检查已存在素材等独立准备；不进入依赖该确认的生图或最终组装工作。
- 宿主没有专用提问工具时，用普通消息展示成果并结束当前轮等待。不得依靠某个特定宿主的工具才能完成流程。
- 进度消息、内部检查通过、文件已写入、用户沉默、等待超时，都不是用户确认。

### 4.2 直接完成模式

用户明确表示“直接做完”“不用确认”“你来决定”时，记录用户委托的范围，跳过该范围内的创作确认等待。仍依次展示简短草稿摘要、实际样图和最终结果；无需为了模拟多轮流程而机械停止。

直接完成模式仍先生成代表样图，由 Agent 自检后再补齐，且优先复用样图。已有图片和明确视觉基准足够时可省略新样图生成。

“使用某技能制作网页”本身不等于明确委托所有创作决定。普通任务请求采用默认协作模式；用户明确给出的完整文案、图片或决定则直接复用。

跳过创作确认不扩大既有预算、上传、发布或其它操作的授权范围。本方案不另设通用权限流程，继续遵守当前技能已有的相关约定和宿主高优先级规则。若宿主明确要求不中断完成工作，应尽可能保留阶段可见性，并如实说明执行模式；技能不能覆盖宿主规则。

### 4.3 已明确的决定与局部跳过

| 已有输入 | 处理方式 |
|---|---|
| 用户只给出故事名 | 提出完整草稿和视觉建议，等待 A |
| 用户指定画风，但未给实际文案 | 不再询问画风，A 只确认未定的文案与分镜 |
| 用户提供最终逐幕文案，并要求照此制作 | A 视为已由明确指令覆盖；展示简短映射，不要求重复确认 |
| 用户提供可直接使用的全套图片 | 不生成新样图；必要时确认未定的文案或顺序 |
| 用户已经接受当前故事的角色与样图 | 复用 B 的决定，不再生成另一套方向样图 |
| 用户只要求修改一处文字 | 直接完成授权修改，不重启完整制作流程 |

用户回复“继续”只接受当时明确展示的范围。不得把对文案的接受解释为接受尚未展示的画风样图。若用户说“按这个方向把剩下的都做完，不用再问”，则记录为对后续创作的明确委托。

### 4.4 用户反馈的解释

- “很好，但第 3 幕改成……”是有条件的修改要求，先处理修改，不能把被修改版本标为已确认。
- “第 3 幕改成这句，然后继续”已授权执行明确修订并继续，不再为原样落实的修改增加确认。
- 修改要求仍需要选择新的情节或视觉方案时，展示受影响部分，等待该部分决定，其他已接受部分保留。
- 用户临时问进度时，答复当前成果与等待点，不把问题本身视为继续授权。

## 5. 分阶段执行契约

### 5.1 阶段 0：建立任务与合理默认值

读取用户已有要求，检查已有项目、图片和可用生成能力。决定是否需要新图、是否有未决创作内容、采用何种交互模式。

针对信息很少的《小红帽》请求，先提出可修改的默认方案，例如中文、约 6 幕、适合亲子阅读、童话插画、温和呈现危险情节，并明确这是本次改编建议。不要先发长问卷，也不要把建议称作用户已确认的需求。

童话存在不同版本，第一阶段应明确本次采用的结局和主要改编。没有依据时不要声称严格复现某个版本。用户要求忠于特定文本时先依据该文本整理；事实型内容继续执行现有研究要求。

在生成前按现有规则说明拟新增图片数、样图数及修正上限；授权记录存在时直接复用，不重复提问。

完成条件：用户给定内容与 Agent 提议有区分；已识别当前第一个未决确认点；没有因为缺少可合理默认的小参数而阻塞草稿制作。

### 5.2 阶段 1：故事草稿与确认点 A

草稿必须覆盖最终要显示的实际文案，而不只是标题大纲。短故事在对话中完整展示；较长内容提供同源的可读文件链接并给出整体结构，保证每幕正文都能被审阅。

展示内容：

1. 一小段总体提案：受众、改编方式、结局、幕数、画风及角色要点。
2. 逐幕编号、标题、正式正文、主导画面事件。
3. 必要的少量未决问题，集中成一次反馈。
4. 下一步会生成哪些样图，以及用户如何继续或修改。

对话示例，以下仅演示结构，不是固定要求所有故事套用相同文案：

> 已整理为 6 幕，建议采用温和的童话插画，并保留“获救后与外婆团聚”的结局。以下是将显示在网页上的文案，目前尚未生成图片。
>
> **第 1 幕：出发探望外婆**  
> 文案：小红帽提起装着点心的小篮子，准备去探望住在森林另一边的外婆。临行前，妈妈叮嘱她沿着小路走，不要在路上逗留。  
> 画面：小红帽站在家门前向妈妈告别，红斗篷和篮子是后续保持一致的特征。
>
> 其余各幕同样展示实际正文与画面描述。
>
> 如果这个故事安排合适，回复“继续”即可；也可以直接说“第 3 幕改成……”。确认后我先生成代表样图给你看。

实现时不能用“其余各幕略”替代真实草稿；上面的省略仅用于说明交互格式。

数据约定：尽早将正式拟用正文写入 `content/story.json`，保持其为唯一正文来源。可以先写好合法的预期图片路径，实际图片未生成时明确项目仍为草稿。此时不启动正式验收，不用占位图伪装已完成，也不调用正式分镜导出器绕过缺图限制。

用户可见编号来自当前章节顺序；内部 ID 稳定不变。对话中的“第 3 幕”必须映射到当前故事的第三个章节 ID。

完成条件：每幕实际正文可审阅；当前修订已记录；未接受的草稿没有触发样图生成。A 被接受或被明确委托后才进入阶段 2。

### 5.3 阶段 2：代表样图与确认点 B

样图数量按能否验证方向决定：

- 简单短故事通常 1 张起步。
- 多角色、跨场景或情绪跨度较大时，通常选择 2～3 张。
- 选择能验证关键角色和视觉风险的场景，不机械要求“开头、中间、结尾”。
- 样图计入最终图片总数，达到要求后直接成为正式素材。

将 `prompting.md` 中无条件先生成中性角色参考图的要求改为按需：有用户参考图、已接受样图足以锚定身份时优先复用；确实需要额外角色图时说明用途、计入预计新增图片数，并遵守已有预算范围。

保持现有图片模型和质量默认值。本次不通过默认降低分辨率来换取表面上的成本下降。若用户明确接受低分辨率草图，说明正式阶段可能需要重做，不能把它计作零额外调用的可复用样图。

展示实际图片、所属幕号、简短检查要点，确保用户能够看到图本身。只给文件路径或工具成功日志不算样图展示；宿主不支持内嵌图时提供可打开文件并明确入口。

当前 `contact_sheet.py` 要求全套图片存在，因此首版此处直接展示单张样图，不改故事章节列表以迁就工具，不填补假图片，不运行必然失败的全量总览。

确认问题聚焦角色、画风和场景表达。不要要求用户审阅原始模型提示词或 JSON。

完成条件：样图已生成并实际展示；接受、待修改或委托继续的状态明确；未确认样图没有触发其余图片的批量生成。

### 5.4 阶段 3：补齐图片与完整总览

复用已接受的样图、人物参考和风格依据，只生成缺少或明确需要修订的场景。生成前简短说明剩余数量，例如“已采用 2 张样图，接下来补齐其余 4 张”。

Agent 先检查角色、关键道具、场景语义、文字水印和裁切可用性；失败项在已授权尝试范围内处理。全部图片存在后运行现有压缩与总览工具。

用 `contact_sheet.py --output` 将最终总览保存到项目的 `docs/review/contact-sheet.png`，通过宿主本地图片展示能力展示它。该文件是审阅辅助材料，不要求通过故事预览服务器公开；不修改服务器白名单。

总览带当前顺序编号和简短标题，并允许打开对应大图检查细节。总览只能用于快速检查整体，小缩略图不能证明人物或细节完全正确。

默认展示后继续网页组装，并明确“可以按幕号提出修改”。这是可见性节点，不是隐含的第三个等待点。用户要求逐张审核或先等反馈时才暂停。

完成条件：全套图片可见，缺失或未通过检查的素材没有被当作完整成果；未重复生成已接受样图。

### 5.5 阶段 4：网页组装与交付

按现有模板组装，继续执行数据、媒体、浏览器和响应式检查。分镜导出仍按用户需要或已约定的交付范围执行；阶段审阅不自动增加正式海报、视频或其它成品。

最终回复给出故事页预览、项目路径、简要验证结果及自然语言修改示例：

- “第 3 幕文案短一些。”
- “第 5 幕的狼不够友善，换一张，其他图片保留。”
- “手机上第 2 幕的文字挡住人物了。”

用户不需要编辑 JSON 才能提出修改。可以提供 JSON 作为高级编辑入口，但不要将手动编辑交给用户作为默认修订流程。

完成条件：正式成品通过既有交付校验，实际存在的交付项与说明一致，维护信息仍足以支撑后续局部修改。

## 6. 轻量持久化与单一事实来源

### 6.1 文件职责

| 路径，相对生成项目根目录 | 责任 | 写入方式 |
|---|---|---|
| `content/story.json` | 正式拟用/已采用的正文、顺序、稳定 ID、图片路径及镜头描述 | 始终在这里改正文；草稿与完成态使用同一契约 |
| `docs/production-spec.md` | 创作要求、未决事项、当前阶段、交互模式、修订号、接受记录和 ID 映射 | 复用既有文件，维护精简状态块 |
| `prompts/style-preamble.txt` | 已选风格的实际生成依据 | 复用既有位置，不再在多个文件全文重复 |
| `docs/production-spec.md` 中的角色设定 | 稳定角色特征和引用图片位置 | 仅保留需要复用的最终设定 |
| `prompts/stills/<chapter-id>.txt` | 当前已采用图片实际使用的完整提示词 | 只在有生图时按幕保留；候选实验先写临时目录 |
| `docs/image-qa.md` | 当前采用素材、生成/编辑参数、参考图路径、检查结果 | 复用既有文件，按 ID 定位，不抄录整篇故事 |
| `docs/review/contact-sheet.png` | 当前完整图片总览 | 全图齐备时由现有工具生成 |
| `exports/storyboard.md` / `.html` | 正式分镜成品 | 从故事数据生成；不手改 |
| 系统临时目录 | 废弃候选、分析草稿、临时拼接提示词、临时帧 | 完成替换验证后按现有约定清理 |

可选的长故事文案预览保存为 `docs/review/story-draft.md`，必须明确是从当前故事数据生成的只读审阅副本，标注修订号，修改从 `story.json` 开始再同步。短故事无需额外落这份文件。首版不要求新增自动导出程序。

正式交付时保留当前已采用图片的完整生成提示词；临时目录清理不删除它们。可复用依据不等于精确重现保证：同样提示词和参考图仍可能产生不同图片，说明中不得承诺逐像素重现。

只保留实际获得的模型、参数、参考图和素材来源信息，不伪造种子、任务 ID 或供应商未返回的字段。记录不包含凭证。私有参考信息留在生产文档中，不抄入公开的 `content/story.json`。

### 6.2 production-spec.md 状态块建议格式

以下是记录格式示例，不是要求增加解析器：

```markdown
## 当前执行状态

- 交互模式：协作 / 直接完成
- 模式依据：用户哪条明确要求；未指定时写“默认协作”
- 当前阶段：故事草稿 / 代表样图 / 补齐图片 / 网页组装 / 已交付 / 局部修订
- 当前修订：r2
- 正在等待：文案与方向 / 样图 / 无
- 下一步：具体动作及涉及的章节 ID
- 新图计划：总数、已采用数、剩余数、额外角色图数
- 生成限制：已约定范围或现有授权记录的位置

## 当前顺序与稳定 ID

| 当前幕号 | 章节 ID | 当前标题 |
|---|---|---|
| 1 | 01-departure | 出发探望外婆 |

## 当前有效决定

| 范围 | 对应版本或素材 | 状态 | 依据 |
|---|---|---|---|
| 故事文案与视觉提案 | r1 | 用户已接受 | 对 A 的明确反馈摘要 |
| 样图 01-departure | 实际图片路径 | 等待反馈 | 已展示，尚无用户决定 |
| 其余已生成图片 | 对应 ID 与路径 | Agent 检查通过 | 不能标作用户逐图确认 |
```

修订号仅用于人和 Agent 判断所讨论版本，不强制加入故事 JSON。记录当前有效决定及必要的修改依据，避免无限追加完整对话。状态更新应与实际文件一致；不要只更新状态而漏改产物。

区分“用户接受”“用户委托 Agent 决定”“Agent 自检通过”“未审阅”。一次接受画风不代表用户逐张接受了后来生成的全部图片。

### 6.3 旧项目与中断恢复

1. 先读取当前故事、生产说明、图片检查记录及现有素材，而不是重新初始化故事。
2. 以实际文件和最新用户指令核对记录；发现记录声称图片存在但文件缺失时报告差异，不信任过期状态。
3. 有有效接受记录则复用，只恢复未完成步骤。已经生成但尚未展示/接受的样图应先展示，不默认重生。
4. 旧项目没有状态块时，按当前任务按需补最少记录；不能把没有记录解释成“从头重做”，也不能凭空写成“用户已确认”。
5. 用户针对旧成品提出明确局部修改，即可执行该项修改；不必追问整套故事曾如何被批准。
6. `--force` 会刷新模板和脚本，本次局部修订不应以重新初始化作为惯例。技能源更新不会自动升级现有输出项目，只有具体需要时才有选择地更新相关脚本。

本版不在模板中新增包含默认状态的 `production-spec.md` 或占位提示词文件，以免刷新模板时覆盖真实记录。若实现偏离此决定并引入模板文件，必须同时检查保护路径并增加覆盖保护测试。

## 7. 局部修改与影响范围

### 7.1 变更矩阵

| 用户修改 | 最小需要更新的内容 | 通常保留的内容 | 确认处理 |
|---|---|---|---|
| 错别字、缩短正文、不改变事件含义 | 对应章节正文、现有分镜导出、网页阅读检查 | 图片、角色、画风和其余章节 | 明确请求直接执行 |
| 某幕情节或关键对象变化 | 对应正文、画面描述；检查该图及后续相关情节 | 无关章节与素材 | 有新的创作选择时只确认受影响范围 |
| 单张图片的表情、构图或细节 | 对应图片、生成依据、WebP、总览及现有分镜 | 其余已接受图片与正文 | 明确修改直接执行，范围不清才澄清 |
| 某个重复角色的全局外形 | 角色设定及所有出现该角色的相关图片 | 无该角色的图片、无关正文 | 展示涉及幕号，再按授权范围执行 |
| 全局画风 | 风格依据、代表样图及全部受影响图片 | 已接受正文和章节结构 | 协作模式重新经过视觉确认，不重新审整篇文案 |
| 调整顺序或新增/删除章节 | 顺序、编号映射、受影响转折、新增素材和导出 | 仍适用的稳定 ID 与现有图片 | 只展示调整后的结构与受影响正文 |
| 手机遮挡、字体、对比度或留白 | 排版、文案位置/裁切及浏览器检查 | 故事含义和通常可继续用的图片 | 明确请求直接执行；只有图片本身无法满足时才换图 |

“局部修改”不等于永远只改一个文件。Agent 应检查真实关联，例如篮子中的物品改变可能影响后续多幕，但不得以“保持一致”为理由无差别重生整套图片。

### 7.2 执行顺序

1. 将用户的幕号/标题映射为当前稳定 ID；如果章节重排导致含糊，只澄清那一处映射。
2. 说明准备修改的范围，一句话即可；明确授权内的修改无需再索要批准。
3. 先保留当前采用素材，生成候选或修订数据；图片候选通过检查后再替换正式引用。
4. 更新真正受影响的正文、图片或布局，并同步生成依据和状态记录。
5. 更新派生产物：WebP、总览，以及已交付的分镜文件。没有分镜交付需求时不新增正式分镜。
6. 检查修改区域及必要的相邻情节/响应式表现，汇报具体改了哪几幕。

当前 `make_posters.py` 会重压缩目录中的全部 PNG，这是可接受的确定性本地工作；不能因此多调用图片模型，也不要把它误报为模型重生成。后续若测得压缩成为瓶颈，再考虑选择性处理。

稳定 ID 不随显示顺序重排而改名；文件名原有数字前缀也不必跟着变化。展示编号以当前章节顺序为准。重复编辑时避免通过改 ID 制造重复章节或断开的素材引用。

## 8. Token、图片调用与等待成本控制

### 8.1 成本判断

分阶段会增加少量展示、反馈和输入上下文开销；一次通过的简单任务可能消耗更多文本 token。它减少的是后期返工概率和返工范围，不能预先承诺固定节省比例。

可用以下概念关系评估，不将其当作测得数据：

`分阶段净收益 = 避免的预期返工成本 − 新增的阶段展示与交互成本`

分别记录文本 token、图片生成/编辑调用次数、本地处理时间、用户回复次数和总等待时间。图片费用不等同于文本 token，低分辨率预览也不必然更划算。

### 8.2 执行规则

- 技能入口只保留所有分支都需要的规则与清晰指针，详细格式放在 `workflow.md` 等已有参考中。
- 首次完整展示正文；局部修订只展示改动部分及必要上下文，保留完整文件供查阅。
- 确认问题使用用户语言，不输出长风格提示词、角色 identity block 或内部状态 JSON。
- 复用已采用样图，不做“预览图生成一套、正式图无条件再生成一套”。
- 避免默认生成未请求的角色设定板、海报、视频或多套完整风格备选。
- 恢复任务时先读精简状态与相关章节，不默认重读全部历史、图片和参考文档。
- 全局风格变化确实需要多张重做时如实说明，不假装所有修改都能零成本局部处理。

## 11. 验收方案

### 11.1 必须覆盖的行为场景

| 编号 | 输入或操作 | 期望行为 | 关键失败信号 |
|---|---|---|---|
| A1 | 新建《小红帽》故事，仅给主题 | 展示完整逐幕正文和视觉建议，等待 A，图片调用数为 0 | 直接交网页；只报进度；草稿确认前已生图 |
| A2 | 在 A 回复“第 3 幕改一下” | 只修订相关草稿并展示差异，未获继续指令前不生图 | 默认为全部已接受并进入批量生成 |
| A3 | 接受 A | 只生成并展示必要代表样图，等待 B | 一次生成所有剩余图片 |
| A4 | 在 B 要求修改角色外形 | 修改相关样图/设定，保留适用文案 | 重写整个故事；未接受就补齐图片 |
| A5 | 接受 B | 样图复用，补齐剩余图片，展示总览并继续网页 | 样图被无条件重生；默认又增加全图等待 |
| A6 | 初始明确“直接做完，不用确认” | 记录委托、连续执行、阶段产物可见 | 忽略明确委托反复追问；声称用户逐图确认 |
| A7 | 用户给出最终正文和全套图 | 复用既有素材，零新图片模型调用 | 强制生成角色板、样图或替换用户图片 |
| A8 | 交付后修改第 3 幕措辞 | 仅更新相关正文和派生产物，图片调用数为 0 | 重生图片或重启全部确认 |
| A9 | 交付后只替换第 5 张图 | 定位当前第 5 幕 ID，保留其它采用素材 | 其余图片被重生或覆盖 |
| A10 | 接受样图后中断，再继续 | 读取记录和实际文件，复用样图，恢复剩余工作 | 丢失决定、重复生图、重跑全篇草稿 |
| A11 | 重排章节后说“改第 3 幕” | 根据当前顺序映射稳定 ID | 根据文件名前缀误改旧第 3 幕 |
| A12 | 用户要求全局改画风 | 保留文案，重新审代表样图，更新受影响图片 | 重写未要求修改的故事；沿用旧视觉接受状态 |
| A13 | 旧项目没有状态记录，用户要求改字 | 直接修改目标、按需补最少记录 | 要求从头审核所有内容 |

测试观察重点是实际产物、工具调用顺序、图片调用数量、修改文件范围和接受记录。只检查文档里包含“确认”二字不构成验收。

### 11.2 离线检查与真实执行的区分

- 文档一致性检查：检查所有活跃入口和参考文件，清除旧混合评审包、默认额外角色板、清理已采用提示词等冲突要求。
- 静态文件检查：链接和路径有效，YAML 可读取，示例字段符合实际契约，没有发明不存在的 CLI 参数。
- 离线回归：如有代码、模板或脚本复制逻辑变化，使用当前可用且满足依赖的 Python 运行既有测试。
- 行为走查：在可控测试会话中按场景给出反馈，记录 Agent 是否等待与复用。模拟工具结果可验证流程，但必须标为模拟，不声称验证真实图像质量。
- 真实生图验收：在既有凭证和授权范围内进行；执行本实施方案不等于要求为全部测试默认花费图片调用。未做时记录为待验证。

既有离线测试入口示例，执行前解析真实 Python 路径，在仓库根目录运行：

```powershell
& "<已验证可用的 Python 绝对路径>" -m unittest discover -s "skills/sn-motion-html/tests" -p "test_motion_html.py"
```

正式成品仍需要现有 `verify_media.py`、相应导出检查和浏览器检查。工作流优化不削弱媒体完整性、移动端阅读、减少动态效果、正反向滚动和导航的要求。

如果首版仅修改说明文档，不新增镜像实现的单元测试，也不为了“看起来测试充分”反复运行无关检查。行为验收要与脚本回归分别报告。

### 11.3 成本对比实验

用相同模型、相同幕数、同等图片质量、同等需求与反馈，比较旧流程和新流程：

| 实验 | 衡量重点 |
|---|---|
| 首次通过 | 新增展示 token、用户回复次数、实际等待时间 |
| 文案在草稿阶段被纠正 | 避免了哪些后续生成；总 token 与图片调用的实际变化 |
| 修改单幕纯文字 | 图片调用应为 0，是否只处理相关内容 |
| 单图替换 | 其它采用素材是否保持；尝试次数和处理时间 |
| 全局画风调整 | 已确认文案是否复用；样图是否提前暴露方向问题 |
| 中断恢复 | 重读上下文量、重复模型调用数和恢复步骤 |

优先使用宿主或服务实际报告的 usage。无法读取时写“不可得”，字数只能作为代理指标，不能冒充 token 计数。多轮输入、缓存输入、输出和图片调用分开记录；不要只对比最终回复长度。

本次没有实测节省百分比，因此实现文档和交付说明均不应承诺“节省 X% token”。可先确认返工范围正确，再积累多次运行数据评估净收益。

| 人工状态记录频繁出错 | 小型状态校验或记录辅助命令 | 有实测错误再引入；不让前端依赖工作流状态 |
| 经常无法恢复已采用图片依据 | 为最终提示词和参考信息增加轻量校验 | 不做通用资产数据库或无限历史快照 |

这些增强不能作为首版“顺便实现”的理由。若确实需要，单独说明触发证据、改动和新增测试。
